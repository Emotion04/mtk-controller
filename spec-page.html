02原包的保护方案

三层叠加,已全部剥离。强度属于中等——核心逻辑可读。

壳 SecShell — classes.dex 只是 11 个壳类 stub,真实 dex 运行时解密进内存。已脱壳
混淆 NP 管理器 控制流混淆 8.0(v3.1.39)— 注入 4062 个顶层辅助类,方法体块排序
改名 R8 — .source 全被抹成 r8-map-id-<sha>;功能类被改成短名
关键收获

Kotlin 的协程调试字符串保留了原始类名。把字符串里的签名参数顺序与实际 smali 方法签名的参数类型比对,即可定位混淆名——例如第 4 个参数在字符串里叫 MtkCpuTuneController,实际类型是 Ly91;,于是 y91 = MtkCpuTuneController。

03权限与运行模型

原 App 同时支持三种提权模式,桥接类 RuntimeClient 的类名未被混淆,可直接照搬设计。

三种提权模式

模式说明用户门槛
Shizuku通过 Shizuku 取得 system_server 权限,启动常驻 runtime 进程低(推荐)
root直接以 root 启动 runtime高
adb用户手动执行一条 adb 命令激活中

桥接 API(从原包恢复)

object RuntimeClient {
  const val SERVICE_POLL_INTERVAL_MS = 100L
  const val SERVICE_START_TIMEOUT_MS = 5000L

  fun ping(ctx): Boolean
  fun waitForService(ctx, timeoutMs): Boolean
  fun currentStatus(): RuntimeServiceStatus   // CONNECTED / DISCONNECTED / RESTARTING
  fun startCommands(ctx): ServiceStartCommands  // { adb, shell }
  fun startWithRoot(ctx): ServiceActivationResult  // { success, message }

  fun getSystemService(ctx, name): IBinder     // ← 拿任意系统服务
  fun newProcess(ctx, cmd: Array<String>, env: Array<String>, cwd: String): RuntimeProcess
  fun getSetting(ctx, type: RuntimeSettingsType, key: String, def: Int): String
  fun putSetting(ctx, type, key, value, def): Boolean
  fun readCpuTimes(ctx): ServiceCpuTimes
  fun readTemperatureSensors(ctx): List<...>
}

RuntimeSettingsType = SYSTEM | SECURE | GLOBAL。

Shell 执行

构造 /system/bin/sh -c "<cmd>" → newProcess(...) → 读 stdout,30 秒超时。

没有 Shizuku 会怎样

调节功能必须 Shizuku 或 root(写 sysfs / procfs 需提权)。但读频率不需要——scaling_cur_freq 等节点通常 world-readable。所以设计成权限降级:无 Shizuku 时正常显示频率,调节按钮置灰并说明原因、引导授权;部分设置项可走 WRITE_SECURE_SETTINGS(adb 授权)而不依赖 Shizuku。

04CPU 调频

按簇设置频率上下限 + 调速器,而不是单点锁死。

探测

ls -1 /sys/devices/system/cpu/cpufreq/   # → policy0, policy4, policy7, …

每个 policy 目录 = 一个簇。逐簇读取:

节点含义示例
related_cpus簇成员0 1 2 3
scaling_available_frequencies可选频率400000 … 3200000
cpuinfo_min_freq / cpuinfo_max_freq硬件极值400000 / 3200000
scaling_available_governors可用调速器schedutil performance …
scaling_governor当前调速器schedutil
scaling_cur_freq当前频率1800000
多机型适配：原 App 的做法

不要硬编码 policy0/4/7。原 App 能在多机型运行，靠的不是机型白名单，而是运行时探测：扫描 /sys/devices/system/cpu/cpufreq/ 目录，逐个读 scaling_available_frequencies，按实际结果渲染 UI。

唯一的机型特例是厂商路径差异，全 App 只有一处：ThermalZoneReader 检测 Build.BRAND / Build.MANUFACTURER 含 vivo / iqoo 时，把温控根目录从 /sys/class/thermal 换成 /sys/devices/virtual/thermal。这就是全部——默认路径 + 极少量厂商特例。

设置上下限

400 MHz
3.2 GHz 
# 顺序很重要:先 min 后 max,避免 min > max 被内核拒绝
echo <min_freq> > /sys/devices/system/cpu/cpufreq/policy<N>/scaling_min_freq
echo <max_freq> > /sys/devices/system/cpu/cpufreq/policy<N>/scaling_max_freq
echo <governor> > /sys/devices/system/cpu/cpufreq/policy<N>/scaling_governor

UI 约束:min ≤ max,取值必须来自 scaling_available_frequencies。

调速器

governor语义
schedutil默认,内核调度器驱动,平衡
performance始终最高频
powersave始终最低频
userspace用户空间指定(配合 min=max 锁频)

释放 / 恢复

首次调节前先保存原始状态,释放时写回:

# 保存
policyN → { scaling_min_freq, scaling_max_freq, scaling_governor }
# 释放:写回上述三个值

兜底(无保存记录时):写 cpuinfo_min_freq / cpuinfo_max_freq + schedutil。

注意

MTK 的 powerhal / FPSGO 可能重写 scaling_max_freq,所以释放后也要校验是否生效。

原 App 的方式:MTK PowerHAL 协议

原 App CPU 和 GPU 都走这条路,不写 sysfs:

IBinder = RuntimeClient.getSystemService(ctx, "power_hal_mgr_service")
data.writeInterfaceToken("com.mediatek.powerhalmgr.IPowerHalMgr")
data.writeInt(0); data.writeInt(0)
data.writeIntArray(int[])               // (命令 ID, 值) 成对
binder.transact(0x16, data, reply, 0)   // 申请:返回 handler ID
reply.readException(); ret = reply.readInt()
binder.transact(0x17, data, reply, 0)   // 释放:带上 handler ID

命令 ID 由 format("0x%08X", p2 * 0x100 + p1) 生成。申请成功后返回的 handler ID 存进 SharedPreferences(gpu_handler 等键),释放时用 transact(0x17) 带回去——这就是「没有可释放的请求」的由来。

GPU 拉满实际传入(从 s91 恢复):

listOf("0x00c00000", "0", "0x00c00100", "0", "0x00c04000", <freq>, "0x00c04100", <freq>)
未验证

命令 ID 的语义未经真机验证。MVP 建议优先走 sysfs 上下限(更透明可控),PowerHAL 作为兼容层后续再加。

05GPU 调频

原 App 已有 GPU 拉满 / 释放（走 PowerHAL，不走 sysfs），我们要把它扩展成频率上下限。下面三条 sysfs 路径用于读取与精细控制。

原 App 的 GPU 实现

GPU 走的是和 CPU 同一套 PowerHAL 通道：transact(0x16) 拉满，transact(0x17) 释放，返回的 handler 存在 SharedPreferences 的 gpu_handler 键里。UI 文案：GPU 拉满 / 释放 GPU / GPU 已拉满 / 未读取到 GPU 档位。dex 里没有任何 gpufreq sysfs 路径——说明原 App 完全依赖 PowerHAL。

探测(按优先级)

优先级判据方案
1/proc/gpufreqv2/fix_target_opp_indexGPUFreq v2(新天玑,9300+ 大概率是这)
2/proc/gpufreq/gpufreq_opp_freqGPUFreq v1(老天玑)
3/sys/class/devfreq/mtk-mali/devfreq(Mali 标准框架)
4/sys/kernel/ged/hal/gpu_utilizationGED(仅读利用率)

读

cat /proc/gpufreqv2/gpu_working_opp_table   # v2:OPP 表
cat /proc/gpufreq/gpufreq_opp_dump          # v1:OPP dump
cat /proc/gpufreq/gpufreq_var_dump          # 当前频率(或 devfreq cur_freq)
cat /sys/kernel/ged/hal/gpu_utilization     # 利用率

设置

上下限(推荐,devfreq)

echo <freq> > /sys/class/devfreq/mtk-mali/min_freq
echo <freq> > /sys/class/devfreq/mtk-mali/max_freq
echo <governor> > /sys/class/devfreq/mtk-mali/governor

锁定(gpufreq v2)

echo <opp_index> > /proc/gpufreqv2/fix_target_opp_index   # 0 = 最高频

上限(GED)

echo 1 > /d/ged/hal/custom_upbound_gpu_freq

释放

echo -1 > /proc/gpufreqv2/fix_target_opp_index    # v2 解锁
echo 0  > /proc/gpufreq/gpufreq_opp_freq          # v1 解锁
# devfreq:写回保存的原始 min_freq / max_freq
防覆盖(重要)

MTK 的 GPU DVFS 由固件(MicroP / MFlexGraphics)管理,厂商 power 服务 / GED / FPSGO 可能覆盖用户设置。对策:前台服务 + 定时重申(社区模块普遍用 5 秒间隔),并在 UI 上明示「已被系统覆盖,已重新应用」。

项来源

08架构建议

app/                 Compose UI(主页、CPU、GPU、设置)
core/runtime/        Shizuku / root / adb 桥接(照搬 RuntimeClient 设计)
core/sysfs/          节点探测 + 读写封装(探测式,不硬编码路径)
feature/cpu/         CPU 簇模型、上下限、governor、释放
feature/gpu/         GPU 探测、上下限 / 锁定、防覆盖重申
feature/tweaks/      小功能(命令表驱动)
  • 探测式 — 所有节点路径运行时发现,UI 按实际支持渲染
  • 状态持久化 — 保存原始值,保证「释放」可靠
  • 命令表驱动 — 小功能用数据描述(名称 / 命令 / 开关值)
  • 前台服务 — 防覆盖重申需常驻(带通知)

09风险与待验证

风险影响缓解
无真机验证节点路径可能与 9300+ 实际不符探测式设计;需在设备上跑一次探测
GPU 固件覆盖设置被系统回滚周期性重申 + UI 明示

OTA 后节点变化功能失效探测失败时优雅降级
